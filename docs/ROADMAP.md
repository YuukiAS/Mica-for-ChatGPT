## 1.1 GPT-6 当前界面适配与前端验收的明确分工（对应 06—09）

### “UI 已确定”分别指什么

- **设计方向已有，但正式前端尚未最终通过。** 2026-10-12 的 [Foundation UI Freeze](product/MICA_FOUNDATION_UI_FREEZE.md)固定了扩展弹窗的结构、设计语言、按钮数量与边界；它只证明设计方案被接受，不证明最新 GPT-6 页面里实际按钮位置或混排内容得到支持。最新 0.5.16 模拟页面、popup、PDF 的截图都不能替代当前登录态 UI 的直接证据。
- **ChatGPT 页面适配未完成。** [当前能力合同](../contracts/chatgpt/current.json)里的 `answer.actionCluster`、`answer.math`、`lifecycle.streamingEditBranchTools` 等仍未证明。GPT-6 自 2026-10-07 支持逐步生成的智能交互界面；这是比普通复制按钮定位更广的适配对象，不得漏掉。
- **模型名不是页面结构版本号。** 不因为 `GPT-6` 就假设所有用户拥有相同 DOM，也不按单一模型字符串选择注入器。不同模型/模式、内容类型、工具、实验变体、亮暗主题和窗口尺寸按**可观察的具体能力**匹配，未知局部只停用依赖该能力的功能。

### 针对 GPT-6 的内容保真规则

1. **回答内容先分类，再允许操作。** `AnswerDocument` 在适配器中区分已支持的静态正文/数学、可验证的非交互快照、未知或动态交互内容、仍在渐进生成的内容；每类明确来源、终态和保真能力。
2. **不能把生成中的 UI 当作可持久的完整回答。** 文字已经出现、原生按钮已经出现、图表部分显示均不足以单独证明全部交互内容已稳定；需要终态/版本身份的可信证据，缺失时拒绝永久完整导出。
3. **不擅自承诺活交互的 PDF/Markdown 等价。** 可保真的静态含义可以导出；图表、按钮、表单等如不能保留实际功能，就只能在充分声明后提供非交互表示，或清楚拒绝完整导出。不得截屏充当可选择数学的文本层，也不得遗漏内容后宣称完整。
4. **按能力局部降级。** 普通静态回答仍可安全复制时，不要因某个未知图表关闭整个扩展；涉及不完整回答的“一键完整导出”必须如实失败或显式呈现降级范围。
5. **多端仅验证承诺的页面。** 本轮 Chrome/Edge 桌面版的真实 ChatGPT 优先；macOS Chromium 与目标 8 GB MacBook Neo 的使用归 H1。无需为原生手机 App/Work 桌面壳复制一套未获授权的宿主适配。

## 2. 用户到底要打开真实浏览器几次？

以下计算的是**一次集中人工介入会话**，不是网页标签数、刷新数或单个点击数。Codex 可以自己在隔离 Chromium 上运行任意次本地测试，不计算用户介入。真实登录态和 MacBook Neo 不交给 Codex 自动操纵。

| 节点 | 触发前提 | 用户具体做什么 | 能否由 Codex 独立完成 |
|---|---|---|---|
| **H0：提前只读校准（可选）** | **仅当**步骤 06 检查公开只读 ChatGPT 后，仍无法证明内联回答操作区或 GPT-6 交互内容结构，而这些又是实现步骤 07 所承诺功能的不可替代前提 | 安装预先自测的去敏只读采集入口，在自己的登录态 ChatGPT 中打开已有普通/交互回答，导出一份有界结构报告；不发送新消息、不做功能回归，也不收集聊天正文 | 能从公开页面取得精确合同，则 **H0=0**；否则 **H0=1**。必须先写明具体缺什么，不得凭空让用户试 |
| **H1：首次核心发布验收（必需）** | 步骤 05—08 完成，候选冻结，自动测试和独立审查已通过，安装包可在 MacBook Neo 直接加载 | 在 8 GB MacBook Neo 上一次集中验收（含已有 GPT-6 普通及可取得的交互回答、短/长对话、复制、高亮/PDF、低内存开关与恢复）并提交去敏结果；无特定交互样本时标记未证 | 无法由离线模拟完全替代；计划 **1 次** |
| **H2：完整产品发布验收（计划）** | 步骤 11—13 完成并通过离线/独立验收，需核对 Notion 真实公式和新增安全敏感能力 | 在同一次事先设计好的会话中核对 ChatGPT、一个允许的网页和 Notion，安全能力不得强迫模拟危险发送 | 当前规划 **1 次**；若外部目标可以合法独立验证，则可减少用户动作 |

- **直到首次核心预发布：计划需要用户 1 次，最坏预期 2 次（H0+H1）。**
- **直到完整产品首版：计划需要用户合计 2 次，H0 必需时为 3 次（H0+H1+H2）。**
- 这是**正常推进路径的人工预算，不是无条件保证**。若真实验收发现新问题、修复后旧证据失效，先在真实派生夹具复现并自动回归；只有仍有不可由独立证据证明的重大真实风险时，才提出额外人工请求，并说明理由、范围、风险和是否改为受限发布。不得悄悄增加人工测试轮次。
- 任何时候都不得为了少一次人工而伪造 `EXACT`、把模拟数据当物理设备数据、自动访问登录账号，或发布未证实的用户操作。
- **现在不需要用户打开真实 ChatGPT。** 先完成步骤 05，再尽 Codex 自己的能力完成步骤 06；若 H0 不可避免，必须先一次性准备好报告采集入口。

## 3. 下一步只执行步骤 05；步骤 06、07 接续，不再次重规划

**当前唯一下一步：发布安全闸门（05）。**

1. 核查 `settings-model.ts`、`content.ts`、`recovery-controller.ts`、`recovery-state-machine.ts`、`recovery-action-policy.ts` 及后台自动恢复路径。既有默认：`reliability=true`、`autoRecoveryEnabled=true`、`autoReloadEnabled=true`、`maxAutoReloadsPerTurn=2`；真实页控制合同未证，不能假设自动行为永远无法发生。
2. 对首次预发布选择**保守可验证的运行行为**：未经充分实站证明的自动刷新、自动 Stop/retry、自动重发均默认**关闭或硬停用**。旧安装设置迁移及导入设置不得重新开启未批准行为；静态显示、只读诊断与已有功能可保留。保留将来步骤 13 的设置结构，不删除后端。
3. 给所有可能触发 `location.reload()` 的路径建立动作前安全不变量：当前标签页、会话身份、输入框/未发送草稿、流式进展、工具/授权、有副作用操作、提交证据和后台一次性锁；缺任一可信证据不得自动刷新。已有 `inspectReloadSafety()` 必须实际接入相关生产路径或用同等可证实的检查取代，并验证仅修复状态机不能越过运行时执行检查。
4. 按现有测试阶梯新增**旧代码必败、新代码通过**的最小代表性回归（含旧设置迁移、模糊提交、草稿非空、工具执行、跨标签、后台重启及禁用场景）；必要时版本升级并冻结新候选。不得用删除验收门槛或全关四核心功能制造 PASS。
5. 完成后直接进入步骤 06，不创建后续 Goal。先尝试隔离公开只读当前页面证据；若 H0 真正不可替代，停止仅这一依赖，给用户一次最小只读采集动作，其余无需账号的步骤继续推进。

步骤 05—08 必须保留对比旧错误实现的反例和真实安装扩展端到端结果。要让“按钮错位、误绑邻近回答、重复按钮、选区覆盖输入框、PDF 数学不可选、Low Memory 仅隐藏 DOM、自动刷新误触发”在正常验收中失败。

## 4. 两次发布必须满足的产品标准

### 首次核心预发布的硬门槛（第 10 步）

- **交互真实可发现且适配 GPT-6**：回答下面最多一个紧凑的 Mica 操作按钮，必须属于经过当前真实证据证明的回答操作区，并正确响应点击、键盘、切换对话/重挂载；选区高亮入口不长驻。需要同时识别普通文字与已观测的智能交互/渐进回答，不能误绑宿主图表、按钮和表单。确实不能证明内联按钮时安全不注入、保留右键后备，但**不得把右键后备静默声明为内联 UI 已完成**，只能将该项标为受限并请求明确产品裁决。
- **四项核心真实交付**：回答 Markdown/LaTeX 系统剪贴板正确；四色高亮在刷新和重新挂载后可恢复；PDF 继承高亮且中文、正文—行内公式—正文及展示数学可选择/搜索；Low Memory 真截断、能恢复完整服务器历史，且不破坏输入与工具交互。对 GPT-6 智能交互组件，明确说明支持的静态提取范围；若无法完整复制/导出，必须在用户动作处报告限制，不得称完整。
- **界面完整**：弹窗以四核心能力及可信状态为中心；不可用的完整会话导出不能占据显眼主要操作位；设置页常用优先、危险恢复默认关闭并折叠；PDF 正文没有数学回退计数、高亮诊断或内部术语。必须检查真实安装扩展的亮/暗、320—400 px、键盘焦点、滚动和错误状态。
- **测试和审查闭环**：每次影响运行时的修改都更新候选身份、构建和受影响证据；完整候选通过现有验收器，控制样本拒绝误报；Producer 自检 P0/P1/P2 为 0，独立实际产物 Reviewer 和 GPT Work 整体审查已完成；登录态与目标设备 H1 的结果按证据类别记录，不能缺失后依旧宣称正式完成。
- **发布实际可用**：Windows/macOS Chromium 的安装步骤、ZIP/Manifest、版本及 SHA-256 一致；`main`、tag、Release 下载资产、中文发布说明从同一最终候选形成并回读。只有通过门槛才标为 GitHub 预发布，不能自动标稳定版。

### 完整产品首版的追加门槛（第 14 步）

- 普通网页高亮的授权、文章页重挂载/高亮保留及导出已达到声明范围。
- Notion 真实目标的结构与原生数学对象身份有可追溯证据；不能证明就按功能缺口明示，不能称完成。
- 自动断流恢复默认值、误触发、发送去重、外部工具动作及各项阈值配置经过生产执行路径和足够的真实边界证实；高风险功能不能因后端代码存在而自动启用。
- 完整 UI 统一、GPT-6 智能交互回答的支持范围与静态导出限制明确、普通补丁默认离线自动回归、跨站兼容能力逐项失效而非全部崩溃；新版本全部候选证据和独立审查真实绑定。

## 5. 不允许继续发生的交付方式

- 不再连续生成“新的完整 Goal”“新的 Atlas”“验收器的验收器”，也不重新发明已冻结的产品架构；只在这一条路线图里更新步骤状态、提交和未证缺口。
- 不能凭验收器 `20/20` 或视觉基线 `MATCH` 代替登录态当前页面适配与独立产品审查。
- 不允许 Producer 把本地操作成功写成“用户已经可用”；只有“候选构建”“真实登录态验收”“正式发布”三个层级，报告必须区分。
- 不允许发布后仍把测试夹具里的右侧控制面板、Developer QA、日志、内部计数、自动化角色/过程叙事泄漏到正式弹窗、回答菜单或 PDF。
- 同类错误反复出现两次又无新信息，先核查真实证据、fixture 保真度和代码调用链，停止重跑。真实失败必须形成离线旧坏/新好再作一次最小确认。
- `main`、公开 Release、代码分支和用户实际安装包不允许长期无标识地漂移；未发布的开发候选必须明确写“未发布”。
- 仅对**已经完成的步骤**更新状态，并附代码提交、真实执行记录、审查和对应证据链接。受影响代码修改后旧候选验证按冻结合同失效。Roadmap 的“完成”不由提交者自签实站或独立验收。

## 6. 范围与维护
